# AQ OS — نواة أمان مفتوحة المصدر (نموذج أولي)

هذا المستودع يحتوي على نموذج Python قابل للاختبار لسياسات أمان AQ OS، وبداية انتقال تنفيذية إلى Rust. لا ينبغي تثبيته على هاتف أو اعتباره نواة تشغيل فعلية؛ العزل ومخزن المفاتيح والشبكة في نموذج Python ممثلة داخل العملية نفسها، ونواة Rust الحالية ما زالت bootstrap bare-metal.

## التشغيل

يتطلب Python 3.11 أو أحدث وحزمة `cryptography`:

```bash
python3 -m pip install cryptography
python3 test_aqos.py
python3 test_aqos_hardening.py
cargo test -p aqos-policy
cargo build -p aqos-kernel --target x86_64-unknown-none
```

الاختبارات الحالية تغطي 45 هجمة أساسية و6 اختبارات إدخال حدودية إضافية.

تفاصيل انتقال Rust موجودة في [RUST_MIGRATION.md](RUST_MIGRATION.md). طبقة `aqos-policy` تستخدم حاليًا قياسًا غير تشفيري مؤقتًا، لذلك لا يجوز اعتبارها جذر ثقة قبل استبداله بـ SHA-256 موثّق وربطه بـ TEE أو ROM.

## ما تم تقويته في هذه النسخة

- رفض اشتقاق مفاتيح من مخزن غير مهيأ، والتحقق من طول قياسات PCR.
- تحقق صارم من أنواع مراحل الإقلاع، وعدم تحريك عدادات منع الرجوع عند الإدخال غير الصالح.
- جعل مدقق سجل التدقيق يعيد `False` بدل الانهيار عند السجلات المشوهة.
- رفض manifests ذات أنواع غير صحيحة، وحصر طول معرّفات التطبيقات والنطاقات.
- تحقق صارم من المنفذ وراية TLS واسم المضيف في الجدار الناري.
- منع أسماء التخزين `.` و`..`.
- التحقق من نوع الصلاحية وطريقة المنح عند حدود النواة.

## سياسة الخدمات

لا يعتمد النموذج على Google Play Services أو Firebase أو أي خدمة سحابية مغلقة. في نظام فعلي ينبغي استخدام مكونات مفتوحة المصدر وقابلة للاستبدال، مثل:

- نظام البناء والتحديثات: مستودع Git مُدار ذاتيًا مع توقيعات Ed25519 ونسخ A/B.
- الإشعارات والمزامنة: بروتوكولات Matrix أو خدمة خادم ذاتي، دون ربط الهوية بمزود إعلاني.
- DNS: محلل محلي مع DoT أو DoH قابل للتكوين، مع عدم فرض مزود بعينه.
- الوقت: مصادر NTP متعددة مع تحقق من الاتساق، وعدم استخدام الوقت وحده كجذر ثقة.
- الخرائط والبيانات العامة: OpenStreetMap مع خادم Tile أو مزود مفتوح يختاره المستخدم.
- مراقبة الحزم: قوائم تهديدات قابلة للتحقق بالتوقيع، لا قائمة مركزية غير قابلة للمراجعة.

استخدام مشروع مفتوح المصدر لا يعني أنه آمن تلقائيًا؛ يجب تثبيت الإصدارات والتحقق من التوقيعات وبناء سلسلة توريد قابلة لإعادة الإنتاج.

## ما يلزم قبل نظام قابل للاستخدام فعليًا

1. إعادة كتابة الأجزاء الحساسة بلغة آمنة للذاكرة مثل Rust، وتشغيلها فوق microkernel أو TEE حقيقي.
2. ربط `HardwareKeystore` بـ Secure Element/TEE حقيقي مع مقاومة إعادة التشغيل والتلاعب.
3. تنفيذ MMU، عزل العمليات، صلاحيات الملفات، sandbox، وواجهات تشغيل حقيقية بدل القواميس داخل الذاكرة.
4. إضافة تخزين دائم مشفر، إدارة مفاتيح استرداد، وتحديثات A/B موقعة مع rollback آمن.
5. بناء مكدس شبكة حقيقي، تحقق DNS، سياسات شهادات، ومخزن CA قابل للتحديث.
6. إضافة تدقيق خارجي، fuzzing، اختبارات property-based، وSBOM وبناء reproducible.
7. تثبيت رأس سجل التدقيق داخل عتاد موثوق حتى يُكتشف اقتطاع الذيل.
8. إنشاء نموذج تهديد ومراجعة مستقلة لكل تعريف عتاد وبرنامج تشغيل قبل الاستخدام اليومي.

## تحذير أمني

النجاح في الاختبارات يثبت أن التنفيذ يطابق هذه الحالات الاختبارية فقط. لا يثبت غياب الثغرات، ولا يوفر حماية من مهاجم يسيطر على Python أو نظام التشغيل المضيف أو العتاد. لا تُدخل أسرارًا حقيقية في هذا النموذج.
