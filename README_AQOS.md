# AQ OS — نواة أمان مفتوحة المصدر (نموذج أولي)

هذا المستودع يحتوي على نموذج Python قابل للاختبار لسياسات أمان AQ OS، وبداية انتقال تنفيذية إلى Rust. لا ينبغي تثبيته على هاتف أو اعتباره نواة تشغيل فعلية؛ العزل ومخزن المفاتيح والشبكة في نموذج Python ممثلة داخل العملية نفسها، ونواة Rust الحالية ما زالت bootstrap bare-metal.

## التشغيل

يتطلب Python 3.11 أو أحدث وحزمة `cryptography`:

```bash
python3 -m pip install cryptography
python3 test_aqos.py
python3 test_aqos_hardening.py
cargo test -p aqos-policy
cargo run -p aqos-image
cargo run -p aqos-image -- --run
```

الاختبارات الحالية تغطي 45 هجمة أساسية و6 اختبارات إدخال حدودية إضافية.

تفاصيل انتقال Rust موجودة في [RUST_MIGRATION.md](RUST_MIGRATION.md). طبقة `aqos-policy` تستخدم SHA-256 وEd25519 فعليين، والصورة تقلع في QEMU عبر BIOS. ربط مفاتيح التوقيع بـ ROM أو TEE حقيقي ما يزال جزءًا من مرحلة العتاد.

## المرحلة الأولى: إدارة الذاكرة

تم تنفيذها داخل النواة Rust: خريطة الذاكرة الفيزيائية من bootloader، تخصيص إطارات `usable`، صفحات heap بحجم 4KiB، و`LockedHeap` كمخصص عام. يختبر QEMU تخصيص `Box` داخل النواة ويطبع `AQ OS kernel: memory manager OK`.

## المرحلة الثانية: المقاطعات والجدولة

تم تنفيذ IDT، معالجات `page fault` و`double fault`، PIC 8259، timer IRQ، عداد ticks، واختيار round-robin أساسي بين المهام المسجلة. يختبر QEMU ذلك ويطبع `AQ OS kernel: interrupts and timer OK`.

## المرحلة الثالثة: syscall ABI والعزل الأولي

تمت إضافة مكتبة `aqos-syscall` بنمط `no_std` لتعريف أرقام syscalls وبنية ABI ثابتة (`repr(C)`)، وطبقة capabilities تمنح أقل صلاحية لازمة لكل مهمة. يتحقق dispatcher من الصلاحيات قبل تنفيذ `ClockGetTicks` و`ConsoleWrite`، ويتحقق `UserPtr` من العنوان والنطاق ومن تجاوزات الحساب. يختبر QEMU السماح بقراءة ticks ورفض الكتابة إلى الطرفية عند غياب capability، ويطبع `AQ OS kernel: syscall capability gate OK`.

هذه المرحلة ليست user mode مكتملًا بعد: لا توجد حاليًا حلقة دخول `syscall`/`sysret` حقيقية، ولا ring 3 أو جداول صفحات منفصلة أو محمّل ELF. ستُنفذ هذه المكونات في المراحل التالية.

## المرحلة الرابعة: مساحات عناوين user مستقلة

تم تنفيذ أساس العزل الفعلي على مستوى MMU: تنشئ النواة جذر page table مستقلًا لكل مساحة user، تمسح الجذر قبل استخدامه، وتضع خرائط user مع أعلام `PRESENT | WRITABLE | USER_ACCESSIBLE` فقط. تُترك صفحات null غير قابلة للوصول، وتُرفض العناوين خارج نطاق user. يختبر QEMU نفس العنوان الافتراضي داخل مساحتين مختلفتين ويثبت أنه يترجم إلى إطارين فيزيائيين مختلفين، ثم يطبع `AQ OS kernel: isolated user address spaces OK`.

هذه المرحلة لا تبدّل `CR3` ولا تدخل ring 3 بعد؛ جداول kernel المشتركة، تبديل السياق، حماية التنفيذ `NX`، ومسار `syscall/sysret` ستُستكمل في المراحل التالية.

## المرحلة الخامسة: تبديل مساحات العناوين عبر CR3

تم تنفيذ بنية `AddressSpace` التي تحتفظ بجذر Page Table فيزيائي مستقل وتوفر تبديلًا صريحًا عبر `CR3`. تُنسخ خرائط النواة إلى الجذر الجديد باستثناء `PML4[0]` الخاص بنطاق user، ثم تُضاف خرائط user صراحةً فقط. يختبر QEMU التبديل من مساحة إلى أخرى والعودة إلى جذر النواة، ويطبع `AQ OS kernel: user address spaces and CR3 switch OK` دون أخطاء ذاكرة.

التبديل الحالي primitive للنواة ويُستدعى مع تعطيل المقاطعات قبل تشغيل user mode. لم يُنفذ بعد تبديل سياق سجلات كامل، أو ring 3، أو مكدس kernel مستقل لكل عملية.

## المرحلة السادسة: GDT/TSS والدخول الفعلي إلى ring3

تم تنفيذ GDT خاصة بـ AQ OS تحتوي واصف kernel code وواصفات user code/user data بمستوى صلاحية 3، مع TSS ومكدس kernel مستقل عند انتقال المقاطعة من ring3 إلى ring0. تُنشئ النواة صفحة كود user وصفحة stack، تنتقل إلى ring3 عبر `iretq`، وينفذ الكود user تعليمة `int3` التي تعبر IDT بمستوى DPL3 وتعود إلى معالج النواة. يثبت QEMU ذلك برسالتي `AQ OS kernel: GDT and TSS OK` و`AQ OS kernel: ring3 breakpoint trap OK`.

المسار الحالي هو انتقال تجريبي آمن ومحدود، وليس بعد عملية كاملة: لا يوجد محمّل ELF، ولا مكدس kernel لكل عملية ديناميكي، ولا بوابة `syscall/sysret`، ولا حفظ/استعادة سجلات user عند الجدولة.

## ما تم تقويته في هذه النسخة

- رفض اشتقاق مفاتيح من مخزن غير مهيأ، والتحقق من طول قياسات PCR.
- تحقق صارم من أنواع مراحل الإقلاع، وعدم تحريك عدادات منع الرجوع عند الإدخال غير الصالح.
- جعل مدقق سجل التدقيق يعيد `False` بدل الانهيار عند السجلات المشوهة.
- رفض manifests ذات أنواع غير صحيحة، وحصر طول معرّفات التطبيقات والنطاقات.
- تحقق صارم من المنفذ وراية TLS واسم المضيف في الجدار الناري.
- منع أسماء التخزين `.` و`..`.
- التحقق من نوع الصلاحية وطريقة المنح عند حدود النواة.

## سياسة الخدمات

لا يعتمد النموذج على Google Play Services أو Firebase أو أي خدمة سحابية مغلقة. في نظام فعلي ينبغي استخدام مكونات مفتوحة المصدر وقابلة للاستبدال، مثل:

- نظام البناء والتحديثات: مستودع Git مُدار ذاتيًا مع توقيعات Ed25519 ونسخ A/B.
- الإشعارات والمزامنة: بروتوكولات Matrix أو خدمة خادم ذاتي، دون ربط الهوية بمزود إعلاني.
- DNS: محلل محلي مع DoT أو DoH قابل للتكوين، مع عدم فرض مزود بعينه.
- الوقت: مصادر NTP متعددة مع تحقق من الاتساق، وعدم استخدام الوقت وحده كجذر ثقة.
- الخرائط والبيانات العامة: OpenStreetMap مع خادم Tile أو مزود مفتوح يختاره المستخدم.
- مراقبة الحزم: قوائم تهديدات قابلة للتحقق بالتوقيع، لا قائمة مركزية غير قابلة للمراجعة.

استخدام مشروع مفتوح المصدر لا يعني أنه آمن تلقائيًا؛ يجب تثبيت الإصدارات والتحقق من التوقيعات وبناء سلسلة توريد قابلة لإعادة الإنتاج.

## ما يلزم قبل نظام قابل للاستخدام فعليًا

1. إعادة كتابة الأجزاء الحساسة بلغة آمنة للذاكرة مثل Rust، وتشغيلها فوق microkernel أو TEE حقيقي.
2. ربط `HardwareKeystore` بـ Secure Element/TEE حقيقي مع مقاومة إعادة التشغيل والتلاعب.
3. إكمال ring 3، جداول صفحات user منفصلة، مسار syscall حقيقي، ومحمّل ELF.
4. إضافة تخزين دائم مشفر، إدارة مفاتيح استرداد، وتحديثات A/B موقعة مع rollback آمن.
5. بناء مكدس شبكة حقيقي، تحقق DNS، سياسات شهادات، ومخزن CA قابل للتحديث.
6. إضافة تدقيق خارجي، fuzzing، اختبارات property-based، وSBOM وبناء reproducible.
7. تثبيت رأس سجل التدقيق داخل عتاد موثوق حتى يُكتشف اقتطاع الذيل.
8. إنشاء نموذج تهديد ومراجعة مستقلة لكل تعريف عتاد وبرنامج تشغيل قبل الاستخدام اليومي.
